# 2026-11-02 发布说明：身份权限改造与数据看板口径

这次发布**包含不可逆的数据库改动**（删除 6 个旧列），必须停机执行、先备份、先在备份副本上演练。上一个可回滚版本是 `e596315`。

## 1. 发布内容

| 模块 | 变化 |
|---|---|
| 身份权限 | 角色、菜单、区域、领域改为数据库字典；登录改为 JWT 访问令牌加刷新令牌；可有多个超级管理员；新增成员、角色、部门、操作日志页面 |
| 资产归属 | Skill、Agent 的区域和领域标签从 JSON 列搬到关联表，用于按成员归属过滤 |
| 内置数据 | 前端不再回退到内置示例数据；取数失败时提示“数据获取失败” |
| 文档写入 | 公告、AI 快讯、办公场景改为单条写入，不再整表覆盖，避免抹掉别人的改动 |
| 用户分析 | 用户明细和领域活跃统一按“所选区间访问过 5 个页面”统计；新增页面浏览数 PV、累计登录次数；时间统一为北京时间 `yyyy-mm-dd HH:mm` |
| 资产、交互行为 | 去掉时间筛选，全部显示累计值，与门户卡片同源；删除“区间事件数和累计值取较大”的算法 |
| 分享统计 | 新增分享次数；分享链接带编号，只有带有效编号才算分享进入；游客不能分享；已下架资产不计分享和分享进入 |

## 2. 数据库改动

共 6 个迁移，按下面顺序由 `npx prisma migrate deploy` 自动执行。**每个迁移在一个事务里，失败会整体回滚。**

### 2.1 `20261030000000_rbac_identity`：身份字典与成员表

| 表 | 改动 | 对现有数据的影响 |
|---|---|---|
| `role`、`menu`、`role_menu`、`region`、`domain` | 新建，写入内置角色和菜单 | 区域、领域优先取现有 `org-taxonomy` 配置 |
| `member_domain` | 新建 | 由 `member.dept_ids` 展开，保留顺序 |
| `member.email` | 转小写并去首尾空格，改 `NOT NULL`，加小写检查约束 | **有空邮箱或转小写后重复时迁移中止** |
| `member.role` | 改名为 `role_id`，加外键 | `workspace_admin` 变 `super_admin`，`developer` 变 `capability_ops`，其他未知角色变 `business_user`；**超管超过 1 个时迁移中止** |
| `member.region_id` | 加外键 | 空字符串变 `NULL`；字典没有的区域自动补进字典 |
| `member.dept_ids` | **删除（不可逆）** | 数据已搬到 `member_domain` |
| `member.token_version` | 新增，默认 0 | 无 |

### 2.2 `20261030010000_refresh_token`

新建 `refresh_token` 表。现有数据不受影响。

### 2.3 `20261030020000_asset_org_tags`：资产标签搬表

| 表 | 改动 | 对现有数据的影响 |
|---|---|---|
| `skill_region`、`skill_domain`、`agent_region`、`agent_domain` | 新建 | 由旧 JSON 列展开，同一标签重复时只留第一个；字典没有的标签自动补进字典 |
| `skill.owner_dept_ids`、`skill.owner_region_id`、`skill.owner_region_ids` | **删除（不可逆）** | Skill 区域：数组非空用数组，否则用单值 `owner_region_id` |
| `agent.owner_dept_ids`、`agent.owner_region_ids` | **删除（不可逆）** | 数据已搬到关联表 |

工具的标签仍保留在 JSON 列，不受影响。

### 2.4 `20261031000000_menu_tree`：菜单两层与权限收紧

- `menu` 新增 `parent_id`、`fixed`，`role_menu` 新增 `can_edit`。
- 删除菜单 `admin`、`presentation`、`agent-studio`、`cases` 及其授权；组织权限拆成成员、角色、部门。
- **权限收紧：** `business_user`、`viewer` 不再有能力配置、运营、系统、组织权限菜单；`viewer` 不再有 AI 任务、任务记录。
- 新增角色 `member`（普通用户），只有顶部五个菜单。`member.role_id` 默认值改为 `member`，**只影响新成员**，现有成员角色不变。

### 2.5 `20261031130000_operation_log_menu`

新增菜单 `org-audit`，已有组织权限的角色可查看、不可编辑。

### 2.6 `20261102000000_market_share_code`：分享编号

`market_engagement_event` 新增可空列 `share_code` 和索引 `market_engagement_event_share_code_idx`。历史事件该列为 `NULL`，不回填、不改动，已统计的分享进入数不变。建索引期间会阻塞写入表，所以要停机执行。

### 2.7 不改动的表

看板口径调整都在查询层，以下表**没有结构和数据改动**：`market_engagement_stat`、`market_user_vote`、`market_favorite`、`portal_page_view`、`portal_daily_login`、`portal_conversion_event`、`case_insight_article`、`tool`。

## 3. 发布前准备

### 3.1 配置 `apps/api/.env`

| 变量 | 要求 |
|---|---|
| `JWT_SECRET` | **新增且必填**，缺失时 API 启动直接退出。用 `openssl rand -hex 32` 生成，多台 API 必须一致 |
| `SUPER_ADMIN_EMAIL` | **填现有超管的邮箱。** 启动时该邮箱不存在会新建账号，已有的其他超管保持不变。不配置时不改动，只在没有超管时告警 |
| `SUPER_ADMIN_PASSWORD` | 只在该账号还没有密码时写入，不会覆盖已有密码 |

### 3.2 只读预检（线上库）

这段 SQL 只读。**前三项必须都为 0 行，否则先处理成员数据再发布。** 把全部输出保存为 `baseline.txt`，发布后对账。

```sql
-- 1. 没有邮箱的成员
SELECT id FROM "member" WHERE email IS NULL OR btrim(email) = '';
-- 2. 邮箱转小写后重复
SELECT lower(btrim(email)) AS email, string_agg(id, ',') AS ids FROM "member" GROUP BY 1 HAVING count(*) > 1;
-- 3. 超管多于一个（一个或没有时返回 0 行）
SELECT string_agg(id, ',') AS ids FROM "member" WHERE role IN ('super_admin', 'workspace_admin') HAVING count(*) > 1;

-- 以下是基线，发布后要对得上
SELECT 'member' AS item, count(*) AS n FROM "member"
UNION ALL SELECT 'skill', count(*) FROM "skill"
UNION ALL SELECT 'agent', count(*) FROM "agent"
UNION ALL SELECT 'tool', count(*) FROM "tool"
UNION ALL SELECT 'event', count(*) FROM "market_engagement_event"
UNION ALL SELECT 'event_detail_direct', count(*) FROM "market_engagement_event" WHERE action = 'detail_direct'
UNION ALL SELECT 'page_view', count(*) FROM "portal_page_view"
UNION ALL SELECT 'daily_login', count(*) FROM "portal_daily_login"
UNION ALL SELECT 'stat_views', COALESCE(sum(views), 0) FROM "market_engagement_stat"
UNION ALL SELECT 'stat_likes', COALESCE(sum(likes), 0) FROM "market_engagement_stat"
UNION ALL SELECT 'stat_favorites', COALESCE(sum(favorites), 0) FROM "market_engagement_stat"
UNION ALL SELECT 'stat_uses', COALESCE(sum(uses), 0) FROM "market_engagement_stat"
UNION ALL SELECT 'member_domain', count(*) FROM (
  SELECT DISTINCT id, btrim(d) FROM "member", jsonb_array_elements_text(CASE WHEN jsonb_typeof(dept_ids) = 'array' THEN dept_ids ELSE '[]'::jsonb END) AS d WHERE btrim(d) <> '') x
UNION ALL SELECT 'skill_domain', count(*) FROM (
  SELECT DISTINCT no, btrim(d) FROM "skill", jsonb_array_elements_text(CASE WHEN jsonb_typeof(owner_dept_ids) = 'array' THEN owner_dept_ids ELSE '[]'::jsonb END) AS d WHERE btrim(d) <> '') x
UNION ALL SELECT 'skill_region', count(*) FROM (
  SELECT DISTINCT no, r FROM (
    SELECT s.no, COALESCE(NULLIF(btrim(t), ''), NULL) AS r FROM "skill" s, jsonb_array_elements_text(CASE WHEN jsonb_typeof(owner_region_ids) = 'array' THEN owner_region_ids ELSE '[]'::jsonb END) AS t
    UNION ALL
    SELECT s.no, NULLIF(btrim(owner_region_id), '') FROM "skill" s
    WHERE NOT EXISTS (SELECT 1 FROM jsonb_array_elements_text(CASE WHEN jsonb_typeof(s.owner_region_ids) = 'array' THEN s.owner_region_ids ELSE '[]'::jsonb END) AS t WHERE btrim(t) <> '')
  ) y WHERE r IS NOT NULL) x
UNION ALL SELECT 'agent_domain', count(*) FROM (
  SELECT DISTINCT no, btrim(d) FROM "agent", jsonb_array_elements_text(CASE WHEN jsonb_typeof(owner_dept_ids) = 'array' THEN owner_dept_ids ELSE '[]'::jsonb END) AS d WHERE btrim(d) <> '') x
UNION ALL SELECT 'agent_region', count(*) FROM (
  SELECT DISTINCT no, btrim(d) FROM "agent", jsonb_array_elements_text(CASE WHEN jsonb_typeof(owner_region_ids) = 'array' THEN owner_region_ids ELSE '[]'::jsonb END) AS d WHERE btrim(d) <> '') x
ORDER BY 1;

-- 角色换算预期：发布后每个角色的人数应等于这里
SELECT CASE WHEN role = 'workspace_admin' THEN 'super_admin' WHEN role = 'developer' THEN 'capability_ops'
            WHEN role IN ('super_admin', 'capability_ops', 'business_user', 'viewer') THEN role ELSE 'business_user' END AS role_id,
       count(*) AS n
FROM "member" GROUP BY 1 ORDER BY 1;
```

## 4. 发布步骤

1. **停止 API**，公告维护窗口。
2. **备份：** `pg_dump -U mssclaw -Fc mssclaw > mssclaw-$(date +%F).dump`，确认文件非空。这是唯一的回滚依据。
3. **更新代码并迁移**（在仓库根目录）：

   ```bash
   git pull
   npm ci                      # 新增依赖 @nestjs/jwt
   cd apps/api
   npx prisma migrate status   # 必须正好列出第 2 节的 6 个待执行迁移，多了或少了都先停下
   npx prisma migrate deploy
   npx prisma generate
   npm run build
   ```

4. **对账（启动 API 之前）：** 执行 3.4 的 SQL。除超管人数外，任何不一致都先停下，走回滚。
5. **确认 `.env` 后启动 API：** `node scripts/start-api.mjs production`，确认日志没有报错。如果日志出现“已改为能力开发”，核对被降级的人是否符合预期。
6. **发布前端：** `npm run build --workspace @mss-claw/web`，部署 `apps/web/dist`。**前端和 API 必须一起发布：** 前端读 `lifetime` 字段，接口是旧版时数据看板的资产和交互行为模块会报错。
7. **抽查：** 见第 5 节。

### 迁移中止时

迁移因预检失败中止时，当前迁移已整体回滚，但 Prisma 会记下失败。处理完成员数据后执行：

```bash
npx prisma migrate resolve --rolled-back 20261030000000_rbac_identity

```

## 6. 回滚

**只能用备份恢复，不能手工改回或执行反向 SQL**，因为旧列已删除。

1. 停止 API。
2. `pg_restore -U mssclaw -d mssclaw --clean --if-exists mssclaw-备份文件.dump`
3. 前后端都部署 `e596315`，恢复旧 `.env`。

**发布后到回滚之间写入的数据会丢失**（新登录记录、浏览事件、点赞、后台配置等），回滚前先确认影响。

## 7. 发布后的已知变化

这些不是故障，提前告知运营：

- **看板数字变大：** 资产和交互行为改为累计值，比之前显示的区间数字大。
- **分享数据：** 分享次数从 0 开始。已发出的旧链接没有编号，之后打开算系统进入；已统计的分享进入数保留。
- **书签和新标签：** 不再算分享进入，所以分享进入数的增长会比之前慢。
- **累计登录次数是下限：** 2026-08-28 之前只有“当天是否登录”，每个登录日按 1 次算。
- **权限收紧：** 业务用户、只读访客会失去后台菜单，需要的人要在“成员”页调整角色。
