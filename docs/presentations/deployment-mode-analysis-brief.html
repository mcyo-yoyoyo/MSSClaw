DEPLOYMENT STRATEGY BRIEF

部署方式体系化分析方案：云端为主是否足够？

面向公司内部 IT 与产品共建研讨：客观比较常见 AI 平台部署形态，结合 MSSClaw 拟解决的问题、1.0 目标，以及与「员工助手」的职责边界，给出可拍板的部署策略建议。

EXECUTIVE SUMMARY

建议结论：本阶段仅云端部署即可（含内网私有云 / VPC）

MSSClaw 的主价值是组织级场景能力沉淀与任务闭环，不是个人桌面 Agent。 本机文件读写与 CLI 自动化已由员工助手覆盖；平台侧优先保障模型资源、组织权限、审计管控与版本一致性。 因此产品主路径采用云端（优先内网云）即可达成目标；本地端客户端列为明确非目标，避免能力重叠与治理风险。

01研讨背景与问题定义

内部 IT 提出的核心问题通常可表述为：

  • 是否只做云端部署？
  • 是否还需要本地端（桌面客户端 / 本机 Agent / 本地 CLI）？

要答好这两个问题，必须先澄清一个常见混淆：

关键澄清：「内网部署 / 私有化」属于云端形态的托管位置选择（服务仍在服务端，用户浏览器访问）， 并不等于「本地端 Agent」（安装在员工电脑上、读写本机文件、执行本机命令）。两者治理模型完全不同。

本方案采用咨询常用的「先分型 → 再对场景 → 后贴目标 → 再给决策」方法，避免用单一口号代替架构选择。

02部署形态谱系（客观分类）

结合业界 AI 平台与 Copilot / Agent 产品实践，建议将选项收敛为四类：

A. 组织云端（推荐主形态）

公有云 SaaS、企业租户或托管集群；浏览器访问；模型与业务逻辑在服务端。

  • 典型：企业 AI 门户、知识库、任务编排平台
  • 治理：统一身份、配额、审计、发布门禁

B. 内网托管 / 私有云（仍属云端）

部署于公司 VPC / 专有云 / 机房 K8s；数据与推理可不出域。

  • 解决：合规、数据主权、内网可达
  • 不改变：仍是服务端平台，不是桌面 Agent

C. 本地端 Agent（本阶段不主推）

桌面端 / 本地 Runtime / CLI；可访问本机文件系统与命令环境。

  • 典型：个人编程助手、本机文件整理机器人
  • 治理难点：终端异构、密钥分散、行为难审计

D. 混合连接器（高成本选项）

云端大脑 + 受控本地插件 / 企业连接器。

  • 能力最全，但审批、安全、运维成本显著上升
  • 适合有明确本机刚需且可单独立项时再议

另需区分研发本地调试（如 npm run dev）与产品部署形态：前者是工程手段，不构成对最终用户提供「本地端产品」的承诺。

03使用场景与优劣势对照

3.1 场景适配矩阵

使用场景 云端 A/B 本地端 C 混合 D
组织案例学习 / 场景货架 / 培训沉淀 优 弱 中
统一模型供给、成本与版本管理 优 难 中
组织级 RBAC、发布精选、审计留痕 优 弱 中高成本
跨角色协同（业务使用 / 能力配置分离） 优 弱 中
读写本机文件、执行本地 CLI 非主场 优 优（贵）
断网环境下的重度本机自动化 视内网 优 中
与既有「员工助手」边界清晰、避免重叠 优 易冲突 需严格分域

3.2 优劣势摘要

云端（A/B）优势

  • 模型资源可集中保障与弹性扩缩
  • 组织权限、审计、发布流程可落地
  • 版本一致，升级一次全员受益
  • 与浏览器工作流天然契合「学习→准备→开干」

云端（A/B）代价

  • 依赖网络与平台可用性
  • 对「深度本机上下文」支持弱
  • 内网化时需 IT 提供算力/网络/身份对接

本地端（C）优势

  • 本机文件与命令环境触达深
  • 部分场景可离线运行
  • 个人效率工具体验直接

本地端（C）代价

  • 终端环境异构，质量难统一
  • 密钥、日志、行为审计分散
  • 安全面扩大（命令执行、文件读写）
  • 易与员工助手功能重叠，职责不清

04项目目标与能力边界

4.1 拟解决的问题

  • 个人会用 AI，但方法难复用、难传承，组织能力沉淀不足。
  • 案例、准备条件、任务执行割裂，缺少统一主路径。
  • 需要可运营的能力货架（Agent / Skill / 知识 / 权限展示），而不是散落的个人工具。

4.2 拟达成的目标意图（对齐 1.0）

  • 主路径：学习 → 准备 → 开干（找案例与做任务两端贯通）。
  • 建设目标：内网可达样板、区域案例包、洞察工具与 How-to、角色权限与开放策略可管。
  • 价值主张：把个人 AI 能力沉淀为可复演的组织能力。

4.3 本阶段明确非目标

非目标：安装后读取访问本机文件、代用户执行本地 CLI——此类能力与公司员工助手定位重叠，且会显著抬高安全与合规门槛，不纳入 MSSClaw 1.0 主产品范围。

05我司场景研判

将「客观优劣」落到「我司是否需要」时，建议采用三条判定标准：

  1. 目标匹配度：该能力是否直接服务 1.0 组织样板与场景闭环？
  2. 职责分域度：是否与员工助手形成清晰互补，而非重复建设？
  3. 治理可达成度：模型、权限、审计能否以可接受成本落地？
判定项 云端 A/B 本地端 C
服务 1.0 目标 直接匹配 非关键路径
与员工助手分域 清晰互补 易冲突
模型与权限治理 易保障 难统一
本阶段投入产出 高 低（且增加边界风险）

因此，从产品战略而非技术偏好出发：我司场景下「仅云端（含内网云）」足以支撑 MSSClaw 要解决的问题与要达成的目标。

06决策建议与实施口径

拍板口径（建议直接用于 IT 对齐）

  • 产品部署策略：仅云端部署；1.0 优先内网云 / VPC 托管，保障内网可达与合规。
  • 用户交付形态：浏览器访问组织平台；不提供默认本地端 Agent 安装包。
  • 能力边界：平台不主动读写员工本机文件、不执行本机 CLI；相关诉求归员工助手。
  • 工程例外：研发本地调试环境保留，但不作为业务用户部署方案宣传。

对 IT 的协作含义（非开发清单，是责任界面）

  • 平台侧：应用、身份对接、RBAC、审计日志、模型网关/配额、发布流程。
  • IT 侧：内网网络与证书、主机/容器资源、出站模型访问策略（若用外部模型）、备份与可用性。
  • 安全侧：以服务端威胁模型为主；无需按「全员终端 Agent」级别做端点管控扩面。

07风险、例外与演进条件

7.1 需主动管理的风险

  • 把「内网」误等同于「必须本地端」——应用澄清会持续沟通。
  • 业务侧临时要求本机自动化——先导向员工助手；确属平台缺口再评估连接器。
  • 外网 Demo 与内网生产口径混淆——Demo 用于形态验证；生产以 1.0 内网样板为准。

7.2 何时才值得重新打开「本地端 / 混合」讨论

建议设置触发条件（满足多数再立项，避免口头蔓延）：

  • 存在高频、刚需、且员工助手明确无法覆盖的本机操作场景；
  • 安全与合规可接受「受控连接器」模型（最小权限、可审计、可撤销）；
  • 有独立资源与运维责任人，不挤占 1.0 主路径交付。
最终表述建议：MSSClaw 现阶段采用仅云端部署策略（含内网私有云）； 本地端不是技术做不到，而是与产品定位、员工助手边界、组织治理目标不一致，故不纳入本阶段范围。
